--- 4. WHAT THIS RULE ADDS, AND WHAT IT DOES NOT

Said plainly, because half of it was already covered and a proof that overstates
its reach is worse than none.

The redactor already knew this form. `tools/survey.py` has ORG_PATH with its own
OWN allowlist, and `tools/redact_surveys.py --check` FAILED on the planted dump
in step 1 while every test in tests/test_no_leak.py passed:

    REDACT  docs/surveys/stats-2026-09-09.txt: 1 line(s)
              643: href="https://www.linkedin.com/company/77777777/admin/..."
    FAIL 1 dump(s) still carry identifiers the redactor knows how to remove.

So on the DUMPS this is a second, independent net over ground `--check` already
covers - worth having, because that check tests the artefact THROUGH the
redactor's rule list and this one does not, but not a hole that was open.

On the SOURCE TREE the hole was open and this closes it. `--check` never looks
at a .py file, and the fifteen-digit rule cannot see a nine-digit id. An
organisation path written into a selector, a fixture or a docstring was
undetected by anything in this repository until now - which is exactly how the
original leak got in.

STILL NOT DETECTED, by this rule or any other here: an organisation id that is
not on one of these four paths. `urn:li:organization:<id>` is redacted by shape
when a dump is written but is not checked for afterwards; a `fsd_company`
parameter and a bare number in prose are covered by nothing.
