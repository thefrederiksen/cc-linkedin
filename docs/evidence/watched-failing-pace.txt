AND THE TEST FOUND A SECOND DEFECT, IN THE R3 FIX I HAD JUST WRITTEN. Six
concurrent writers wedged permanently on the new lock. On Windows, Python's
open() does not ask for FILE_SHARE_DELETE, so while any waiter has the lock file
open to read who holds it, os.remove raises a sharing violation - and the
release path swallowed that as `except OSError: pass`. The lock then stayed
behind carrying a LIVE pid, which no reclaim rule will ever touch. That is the
R3 defect exactly, reintroduced one layer down by an error handler that treated
"I could not do it" as "it is done". _discard now retries for a bounded three
seconds and logs loudly if it still cannot.

That second defect was not in any inspection. It was found because the fix was
given a test that could fail.
